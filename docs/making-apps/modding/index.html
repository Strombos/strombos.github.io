Modding.

Replace one of Triton's classes with your own version, just for your app. Put the new version in your app's mod/ folder and Triton uses it whenever your app's code needs that class.

Start with Making apps. A mod belongs to an app, so you need a working app first.

What a mod is

A mod is your app's own version of one of Triton's classes. It has the same package and class name as Triton's class, and it lives in the mod/ folder inside your app's folder.

When your app opens, Triton compiles mod/ and loads your version in place of its own, but only for your app. Triton itself and every other app keep the original class.

Each Triton class decides whether it may be modded, with the @ModProtection annotation. Some packages can never be modded at all.

Your first mod

This example makes an app always use dark colours, even when Triton has a light theme. The app asks Triton's ThemeMode class whether the theme is dark, and the mod changes the answer to always be "yes", for this app only.

1. An app that follows the theme

This is the Hello app from Making apps, with one change: it asks ThemeMode.isDark() and picks its colours from the answer.

Hello/Main.java 
import shared.AbstractModule;
import shared.ModProtection;
import echelon.util.ThemeMode;

import javax.swing.JFrame;
import javax.swing.JLabel;
import javax.swing.SwingConstants;
import java.awt.Color;
import java.awt.event.WindowAdapter;
import java.awt.event.WindowEvent;

@ModProtection(ModProtection.Policy.ALLOW_MOD)
public class Main extends AbstractModule {

    private final JFrame frame;

    public Main() {
        frame = echelon.ui.WindowFactory.create("Hello");
        frame.setDefaultCloseOperation(JFrame.DO_NOTHING_ON_CLOSE);

        // Ask Triton whether the theme is dark, and pick colours to match.
        boolean dark = ThemeMode.isDark();
        JLabel label = new JLabel(dark ? "Dark theme" : "Light theme", SwingConstants.CENTER);
        label.setOpaque(true);
        label.setBackground(dark ? new Color(0x1E1E1E) : Color.WHITE);
        label.setForeground(dark ? Color.WHITE : Color.BLACK);
        frame.add(label);

        frame.setSize(480, 320);
        frame.setLocationRelativeTo(null);
        frame.addWindowListener(new WindowAdapter() {
            @Override public void windowClosing(WindowEvent e) { close(); }
        });
    }

    @Override public void start()        { frame.setVisible(true); }
    @Override public void bringToFront() { frame.toFront(); }
    @Override public void hideModule()   { frame.setVisible(false); }
    @Override public void showModule()   { frame.setVisible(true); }
    @Override public boolean isVisible() { return frame.isVisible(); }

    @Override protected void onClose()   { frame.dispose(); }
}

With a light theme, the window says Light theme in black on white. Nothing is modded yet.

2. The mod

Triton's class is echelon.util.ThemeMode, so the mod goes in mod/echelon/util/ThemeMode.java:

echelon/desktop/container/applications/
└── Hello/
    ├── Main.java
    └── mod/
        └── echelon/
            └── util/
                └── ThemeMode.java   Hello's version of Triton's ThemeMode

It has the same package, the same name and the same public methods as Triton's ThemeMode. Only isDark() is different:

Hello/mod/echelon/util/ThemeMode.java 
package echelon.util;   // the same package as Triton's ThemeMode

import echelon.ui.theme.ThemeManager;
import echelon.ui.theme.ThemePolicy;

import java.beans.PropertyChangeListener;
import java.beans.PropertyChangeSupport;

// Hello's own ThemeMode. Inside Hello it replaces Triton's.
public final class ThemeMode {

    private static final PropertyChangeSupport PCS = new PropertyChangeSupport(ThemeMode.class);

    private ThemeMode() {}

    // The change: Hello is always told the theme is dark.
    public static boolean isDark() {
        return true;
    }

    // The rest is kept, so code that calls these still works.
    public static void setDark(boolean dark) {
        ThemeManager.setPolicy(dark ? ThemePolicy.DARK : ThemePolicy.LIGHT);
    }

    @Deprecated
    public static void syncFromCurrentLaF() { }

    public static void addListener(PropertyChangeListener l)    { PCS.addPropertyChangeListener(l); }
    public static void removeListener(PropertyChangeListener l) { PCS.removePropertyChangeListener(l); }
}

3. What you see

  • Close Hello and open it again. The window now says Dark theme in white on dark grey, even though Triton's theme is still light.
  • A Class Modded notice appears: Hello → ThemeMode. Triton's ThemeMode has no @ModProtection, so the mod is allowed and Triton tells you about it.
  • The desktop and every other app still follow the real theme. The mod only changes Hello.
  • To undo it, delete mod/ and open Hello again.

Modding any class

  1. Find the full name of the Triton class: its package and class name, like echelon.util.ThemeMode.
  2. In your app's folder, make mod/ and the folders for that package inside it.
  3. Add a .java file with the class's name, starting with the same package line as Triton's class.
  4. Write the whole class: keep every public method and field Triton's version has, with the same names and types, and change what you need.
  5. Open your app. Triton compiles the mod and uses it.

Triton goes by the package line, not the folder. Keep them the same anyway, so the file is easy to find.

@ModProtection

Annotation shared.ModProtection. Goes on a class.

Triton reads @ModProtection on its own copy of the class you're modding. That decides what happens to your mod:

Triton's class hasWhat happens to your mod
@ModProtection(ModProtection.Policy.ALLOW_MOD)Used, silently.
no annotationUsed, and Triton shows a Class Modded notice naming your app and the class.
@ModProtection(ModProtection.Policy.DISALLOW_MOD)Not compiled. Triton shows a Modification Blocked notice and your app gets Triton's own class.

The annotation on your copy doesn't count. Removing DISALLOW_MOD from your version, or adding ALLOW_MOD to it, changes nothing.

You can put @ModProtection on your own classes too, as Making apps shows for Main. There it records your intent; Triton only checks the tag on its own classes.

Protected packages

Classes in these packages can never be modded, whatever their annotation says:

PackageWhat it holds
shared.*The classes apps build on, such as AbstractModule and ModProtection
echelon.module.vortex.*Vortex, Triton's own class loading
echelon.auth.*Sign-in and security
echelon.desktop.core.*Opening and running apps
triton.boot.*Starting Triton

A mod in one of them is skipped with a Modification Blocked notice. Your app can't add new classes to these packages either: Triton always loads them from itself.

How Triton loads mods

Every time your app opens:

  1. Triton compiles your app into bin/, leaving mod/ out. Your app's code is compiled against Triton's original classes.
  2. It checks every file in mod/. A file in a protected package, or for a class Triton marks DISALLOW_MOD, is skipped with a Modification Blocked notice.
  3. It compiles the rest of mod/ into mod-bin/. Mods can use Triton's classes, your app's classes and the jars in lib/.
  4. It checks mod-bin/ again and deletes any blocked class, including its inner classes, so a class file copied in by hand doesn't get through.
  5. It loads your app's classes from mod-bin/ first, then bin/, then lib/. A class found in mod-bin/ wins over Triton's, unless Triton's is marked DISALLOW_MOD.

If mod/ doesn't compile, Triton shows Mod Compilation Failed and opens your app without any mods. One broken file turns off all of them, so fix it and open the app again.

What a mod changes

  • Only your app. Your version is used when your app's code uses the class. Triton's desktop, its other classes and other apps keep using the original.
  • Only while your app runs. Nothing in Triton's own files changes. Delete mod/ and the next open uses Triton's class again.
  • Copies outside mod/ follow the same rule. If a jar in lib/ or a class in your app has the same name as one of Triton's, Triton checks it the same way. It just doesn't show a notice, because this is usually a library that Triton also ships.

To change a Triton class for the whole of Triton, not just your app, Triton uses Vortex instead. Vortex is a separate system with its own rules; mods don't use it.

Jars and class loading

Each app gets its own class loader. When your app's code needs a class, Triton looks for it in this order:

The class isWhere it comes from
java.*, javax.*, shared.* or a protected packageAlways Java or Triton. Your app can't have its own copy.
In your app: mod-bin/, then bin/, then the jars in lib/Your app's copy, the first one found. If Triton has the same class and marks it DISALLOW_MOD, Triton's copy is used instead.
Not in your appTriton's copy.

Library jars go in lib/

Only the jars in your app's lib/ folder are used, both to compile your app and to run it. A jar at the top of the app folder is not:

  • If the folder has a Main.java, Triton ignores the jar. Code that uses it doesn't compile: package … does not exist.
  • If the folder has no Main.java, Triton runs the first .jar it finds as a program, instead of compiling the folder. That's how a folder holding a ready-made jar becomes a tile. It isn't an AbstractModule app, so mod/ and everything on this page don't apply to it.

Two copies of one class

When your app and Triton both have a class with the same name, Java treats them as two different classes: one loaded by Triton, one loaded by your app. Each side works on its own, but passing an object from one side to the other fails with a ClassCastException such as Foo cannot be cast to Foo, or a LinkageError saying loader constraint violation.

This can happen two ways:

  • A library Triton already has, in your lib/. Your app uses its copy and Triton uses its own, so their objects don't mix. Leave the jar out and use Triton's: if your app compiles without the jar in lib/, Triton already provides that library.
  • A mod of a class whose objects Triton hands to your app. Triton makes objects of its own class, and your code expects your version. Mod classes your app uses directly, like ThemeMode, whose static methods your code calls itself.

The same goes the other way: Triton's classes can't see your app's classes. Triton finds your app through Main, which it loads from your app itself.

Common mistakes

MistakeWhat happens · fix
A package line that doesn't match Triton's classYour class is a new class, not a mod, so nothing is replaced. Copy the package line from Triton's class exactly.
Leaving out a method your app usesYour app was compiled against Triton's version, so it fails when it calls the missing method (NoSuchMethodError). Keep every public method with the same signature.
Adding a new method to the mod and calling it from your appYour app doesn't compile: it's built against Triton's original class, which has no such method. Put new code in your own classes instead.
A mod of a DISALLOW_MOD classModification Blocked, and your app gets Triton's class. Only classes with ALLOW_MOD or no annotation can be modded.
A mod in shared.* or another protected packageModification Blocked. These packages can't be modded.
A compile error in one mod fileMod Compilation Failed, and the app opens with no mods at all. Fix the error.
Expecting the desktop or other apps to changeA mod only affects your app. Triton and other apps keep the original class.
A library jar at the top of the app folderIt isn't used. With a Main.java, code that needs it doesn't compile; without one, Triton runs the jar instead of your app. Move it into lib/.
A jar in lib/ with a library Triton already hasTwo copies of the same classes. Objects passed between Triton and your app fail with Foo cannot be cast to Foo. Leave the jar out and use Triton's.
Modding a class whose objects Triton gives your appClassCastException or LinkageError when your code gets Triton's object. Mod classes your own code calls directly.
Editing or adding files in mod-bin/Triton writes that folder and deletes blocked classes from it. Change mod/ instead.
