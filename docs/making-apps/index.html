Making apps.

Build a Triton App: one Java class that extends AbstractModule, a couple of small settings files, and a folder Triton picks up on its own.

No build tool needed. Triton compiles your app's .java files itself every time the app opens.

What a Triton App is

A Triton App is a folder inside Triton's desktop/container/applications/ folder. That folder is in Triton's main folder, echelon, so the full path is echelon/desktop/container/applications/. Every folder there becomes a tile on the desktop, named after the folder.

When someone opens the tile, Triton compiles the folder's Java sources, loads the class Main and starts it. Main must extend shared.AbstractModule, the base class for every app. It gives Triton one way to start, show, hide, raise and close any app.

Your app runs inside Triton's own Java process, so it can use Triton's classes and Swing directly. That also means it must never call System.exit or close the window with EXIT_ON_CLOSE: that would close Triton too.

Your first app

Make a folder named after your app, for example Hello, in desktop/container/applications/, and add one file, Main.java:

Hello/Main.java 
import shared.AbstractModule;
import shared.ModProtection;

import javax.swing.JFrame;
import javax.swing.JLabel;
import javax.swing.SwingConstants;
import java.awt.event.WindowAdapter;
import java.awt.event.WindowEvent;

@ModProtection(ModProtection.Policy.ALLOW_MOD)
public class Main extends AbstractModule {

    // Keep the name "frame": the bottom bar and window snapping look for it.
    private final JFrame frame;

    public Main() {
        frame = echelon.ui.WindowFactory.create("Hello");
        frame.setDefaultCloseOperation(JFrame.DO_NOTHING_ON_CLOSE);
        frame.add(new JLabel("Hello from Triton", SwingConstants.CENTER));
        frame.setSize(480, 320);
        frame.setLocationRelativeTo(null);
        frame.addWindowListener(new WindowAdapter() {
            @Override public void windowClosing(WindowEvent e) { close(); }
        });
    }

    @Override public void start()        { frame.setVisible(true); }
    @Override public void bringToFront() { frame.toFront(); }
    @Override public void hideModule()   { frame.setVisible(false); }
    @Override public void showModule()   { frame.setVisible(true); }
    @Override public boolean isVisible() { return frame.isVisible(); }

    @Override protected void onClose()   { frame.dispose(); }
}

That's the whole app. Open the Hello tile on the desktop and the window appears. The first open takes a moment while Triton compiles the app.

  1. Main.java has no package line. Triton looks for Main in the default package.
  2. echelon.ui.WindowFactory.create(title) gives you a window in Triton's style. A plain new JFrame(title) works too.
  3. Closing the window calls close(), and close() calls your onClose(). Triton then removes the app's bottom-bar button.

To change the app, edit the files, close the app and open it again. Triton recompiles on every open. If the code doesn't compile, a popup shows the compiler's error message.

AbstractModule

Package shared, in Triton's jar. Every app's Main extends it.

The full class, for reference:

shared/AbstractModule.java 
package shared;

import echelon.module.vortex.Vortexable;
import triton.core.atlas.AtlasTag;

import static shared.ModProtection.Policy.DISALLOW_MOD;

@ModProtection(DISALLOW_MOD) // Reject Modded Compile (Already blocked)
@Vortexable(value = Vortexable.Policy.LOCKED) // Prevent Modification
@AtlasTag(
        category = "Core",
        subsystem = "shared",
        description = "Base class for all Echelon modules providing atomic close lifecycle, on-close listener, and abstract start/visibility contract",
        dependencies = {
                "echelon.module.vortex.Vortexable"
        }
)
public abstract class AbstractModule {
    private final java.util.concurrent.atomic.AtomicBoolean closed = new java.util.concurrent.atomic.AtomicBoolean(false);
    private Runnable onCloseListener;

    private String registeredName;

    public void setRegisteredName(String name) {
        this.registeredName = name;
    }

    public String getRegisteredName() {
        return registeredName;
    }

    /**
     * Final close method ensures consistent cleanup.
     */
    public final void close() {
        if (!closed.compareAndSet(false, true)) return; // already closing
        onClose();
        if (onCloseListener != null) onCloseListener.run();
    }

    /**
     * Override this method for module-specific cleanup (e.g., disposing windows, stopping threads).
     */
    protected abstract void onClose();

    // Other abstract methods
    public abstract void start();
    public abstract void bringToFront();
    public abstract void hideModule();
    public abstract void showModule();
    public abstract boolean isVisible();

    public void setOnCloseListener(Runnable listener) {
        this.onCloseListener = listener;
    }

    /**
     * The currently registered on-close listener, or null. Enables safe
     * CHAINING (wrap-and-delegate) instead of clobbering — required by
     * BottomBarPanel's button lifecycle closure.
     */
    public Runnable getOnCloseListener() {
        return onCloseListener;
    }

    public String getVersion() {
        return "R1";
    }
}

What you write

MethodWhat it should do
public Main()Build your window and state. Don't show anything yet. Triton needs this public, no-argument constructor.
void start()Show the app. Called once, right after Triton registers it.
void bringToFront()Raise your window above the others.
void showModule()Make your window visible again.
void hideModule()Hide your window without closing the app.
boolean isVisible()Whether your window is showing.
protected void onClose()Clean up: dispose windows, stop threads and timers, close files.

What Triton gives you

MethodWhat it does
final void close()Closes the app: runs onClose() once, then Triton's close listener. A second call does nothing. You can't override it.
String getRegisteredName()The name Triton registered this instance under (the tile name, made unique when a second copy is open).
Runnable getOnCloseListener()
void setOnCloseListener(Runnable)		The listener Triton sets to clean up the bottom bar. If you need one of your own, wrap Triton's, don't replace it (see Common mistakes).
String getVersion()Returns "R1". You can override it.

Lifecycle

What happens, in order, from a click on the tile to a closed window:

WhenTriton calls
The tile is openedCompiles the app, then new Main(), then setRegisteredName(…) and setOnCloseListener(…)
Right after thatstart(). The app now has a bottom-bar button.
The bottom-bar button is clickedshowModule(), then bringToFront()
The app is hidden or shown from TritonhideModule() / showModule(), checked with isVisible()
Your code calls close()onClose(), then Triton removes the bottom-bar button and unregisters the app

Opening the tile again while the app is open starts a second instance: a new Main. To keep one window, set limit_instance=["onlyOne"] in directory.properties. Triton then brings the open window forward instead.

Nothing calls close() for you when the window closes. Call it from your window's closing handler, as in Your first app. If you only dispose the window, the app stays registered and its bottom-bar button stays behind.

@ModProtection

Annotation shared.ModProtection. Goes on a class.

@ModProtection says whether a class may be replaced by a mod: an app's own copy of one of Triton's classes. Built-in apps put it on their Main:

import shared.ModProtection;

@ModProtection(ModProtection.Policy.ALLOW_MOD)
public class Main extends AbstractModule { … }
ValueMeaning
ModProtection.Policy.ALLOW_MODThe class may be replaced. Triton loads the replacement silently.
ModProtection.Policy.DISALLOW_MODThe class may not be replaced. Triton refuses the replacement, keeps its own copy and shows a Modification Blocked notice.
no annotationThe class may be replaced, and Triton shows a Class Modded notice when it is.

To replace one of Triton's classes inside your app, with a worked example, see Modding.

Which value to use on your Main

  • ALLOW_MOD is the usual choice. Most built-in apps use it.
  • DISALLOW_MOD says the class must not be replaced. Use it for a class that guards something, the way Triton marks its core classes.

Triton checks @ModProtection on Triton's classes. Your Main is always your app's own class, so the tag on it records what you intend; it doesn't change how your app loads. It's still worth adding, so every app says the same thing in the same place.

Other annotations

AnnotationUse in an app
@AtlasTag (triton.core.atlas.AtlasTag)Optional. Describes the class for Atlas, Triton's map of its classes. Built-in apps tag Main with category = "Application", a subsystem such as "apps.hello" and a one-line description.
@Vortexable (echelon.module.vortex.Vortexable)Not for apps. It controls Vortex, which patches Triton's own classes. Leave it off your app's classes.
Example · Main with both tags 
import shared.AbstractModule;
import shared.ModProtection;
import triton.core.atlas.AtlasTag;

@AtlasTag(
        category = "Application",
        subsystem = "apps.hello",
        description = "Hello: a one-window example app"
)
@ModProtection(ModProtection.Policy.ALLOW_MOD)
public class Main extends AbstractModule { … }

The app folder

Only Main.java is required. Everything else is optional:

echelon/desktop/container/applications/
└── Hello/                     the folder name is the app's name
    ├── Main.java              entry point: default package, extends AbstractModule
    ├── hello/ui/Panel.java    more classes, in packages under the app folder
    ├── desktop_logo.png       tile picture (desktop_icon.png also works)
    ├── icon.java              tile icon drawn in code (optional)
    ├── directory.properties   tile and window settings
    ├── module.properties      search words and Java version
    ├── lib/                   .jar libraries the app needs
    ├── mod/                   your versions of Triton classes (see Modding)
    ├── bin/                   written by Triton: compiled classes
    └── mod-bin/               written by Triton: compiled mods
  • Put extra classes in packages that match their folders, e.g. hello/ui/Panel.java starts with package hello.ui;. Only Main stays in the default package.
  • Every .jar in lib/ is on the classpath when your app compiles and runs.
  • icon.java is compiled on its own to draw the tile, not as part of your app. Keep desktop_logo.png too: it's the fallback if the icon script fails, and the bottom bar uses it.
  • Don't edit bin/ or mod-bin/. Triton rewrites them every time the app opens.

directory.properties

Tile and window settings. Optional; leave out any key you don't need.

Each line is key=value, where the value is a list in brackets, like ["onlyOne"]. A single value without brackets also works. Lines starting with # are comments.

Example · Hello/directory.properties 
# Tile picture
icon=["desktop_logo.png"]

# One window: opening the app again brings it forward
limit_instance=["onlyOne"]
KeyWhat it does
icon=["desktop_logo.png"]The tile picture, relative to the app folder. desktop_logo.png is found without it.
icon_script=["icon.java"]A tile icon drawn in code. icon.java is found without it.
override_iconColor="#6FB3CC"A fixed colour for the drawn icon, instead of the theme's accent colour.
launch_effect=["spin"]Tile animation on launch: none, spin, spin:N, pulse or custom. Leave it out to use the icon script's own effect.
limit_instance=["onlyOne"]onlyOne: never a second window; opening the app again brings the open one forward. allowMultiplePerRequest: the same, but the tile's right-click Launch Another Instance opens one more.
bottombar=["separate"]grouped (default): one bottom-bar button for all the app's windows. separate: one button per window.
bar_button=["false"]No bottom-bar button when the app launches. For launcher apps that only open something else and close.
opens=["txt","md"]File types this app opens from anywhere in Triton. Needs FileOpenable (see Opening files).
tag=["Beta"]The first entry is shown as a badge on the tile. "Shortcut=App" shows App and marks the app this tile opens through. "NotMain" marks the app as not made by Triton in its Properties window.
override_badge="New"Badge text that wins over tag.
override_badgeColor="#2F6F8F"Badge colour.
disallow=["nameChanges"]Stops people renaming the tile.

module.properties

Plain Java properties: key=value, no brackets. Optional.

Example · Hello/module.properties 
# Words that find this app in the start menu, comma separated
tags=hello, example, greeting

# Java version to compile for (capped at the Java Triton runs on)
java.version=21
KeyWhat it does
tags=hello, exampleSearch words for the start menu, comma separated.
java.version=21The Java version Triton compiles the app for. Leave it out to use the Java Triton is running on; a higher number is lowered to that.
triton.min=p156-b1The oldest Triton release the app works on. Package installs give an older Triton an older version of the app, or none. Read by Triton Prototype 156 and newer.

Opening files

To make your app open files clicked anywhere in Triton (the desktop, Folder Explorer, open-file), list the file types in directory.properties and implement shared.files.FileOpenable on Main:

directory.properties 
opens=["txt","md"]
Main.java 
import shared.AbstractModule;
import shared.files.FileOpenRequest;
import shared.files.FileOpenable;

public class Main extends AbstractModule implements FileOpenable {
    …
    @Override
    public void openFile(FileOpenRequest request) {
        java.io.File file = request.file();
        // show it in your window
    }
}
  • openFile runs on the Swing thread, after start(). Your window already exists.
  • When the app is already open, Triton calls showModule() and bringToFront() first, then hands the file to that window.

How Triton loads an app

Useful to know when something doesn't start:

  1. The desktop lists every folder in desktop/container/applications/ as a tile.
  2. On open, Triton checks limit_instance. If the app may only run once and is open, it brings that window forward and stops here.
  3. Triton collects every .java file in the folder and its subfolders, except mod/, bin/, mod-bin/ and the icon script. If there's no Main.java, it stops with has no Main.java.
  4. It compiles them into bin/ against Triton's classes plus the jars in lib/. Errors stop the launch and show the compiler output.
  5. It compiles mod/ into mod-bin/, after removing mods that @ModProtection blocks.
  6. It loads Main from your app (mod-bin/, then bin/, then lib/) and checks that it extends AbstractModule.
  7. It calls new Main(), registers the app, and calls start().

Installing and sharing

To install an app by hand, copy its folder into desktop/container/applications/. The tile appears on the desktop under the folder's name.

To share an app, zip its folder without the files Triton writes:

  • Leave out bin/ and mod-bin/. The other person's Triton compiles the app again.
  • Leave out .package if the folder has one. It's the receipt Triton writes when it installs an app from a package.

Apps from the Triton Store and Package Manager arrive the same way: Triton unpacks the zip into desktop/container/applications/, keeps the old copy until the install succeeds, and writes the .package receipt.

The folder name is the app's name: it's the tile's label and the name Triton registers the app under. Pick it before you share the app, because renaming the folder renames the app.

Common mistakes

MistakeWhat happens · fix
A package line in Main.java"has no Main class". Remove the line: Main lives in the default package.
Main doesn't extend AbstractModule"The module's main class does not extend AbstractModule." Extend it.
No public no-argument constructorTriton can't create the app. Add public Main().
EXIT_ON_CLOSE or System.exitCloses all of Triton. Use DO_NOTHING_ON_CLOSE and call close().
Disposing the window without calling close()The bottom-bar button stays and the app stays registered. Call close() and dispose in onClose().
Showing the window in the constructorShow it in start(), which runs after Triton has registered the app.
Calling setOnCloseListener with your own listenerReplaces Triton's, so the bottom bar never cleans up. Put cleanup in onClose(), or wrap Triton's: read getOnCloseListener() in start() and call it from yours.
Threads or timers left runningThey keep running after the window closes, inside Triton. Stop them in onClose().
Classes in shared.*, echelon.auth.* or another protected packageNever loaded from your app; Triton always uses its own. Use your own package name.
A mod of a DISALLOW_MOD class"Modification Blocked", and Triton keeps its own class. Only classes without the annotation, or with ALLOW_MOD, can be modded. See Modding.
A jar in lib/ that Triton also shipsYour copy is used, unless Triton's copy is marked DISALLOW_MOD. Check the Triton log if a library behaves differently than expected.
Using classes from icon.java in your appicon.java is compiled separately, only to draw the tile. Keep app code in other files.
