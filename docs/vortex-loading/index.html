Vortex Loading.

Vortex is Triton's own class loader. It lets you replace one of Triton's classes, or add new ones, by dropping files into a folder. No rebuilt jar needed.

Drop .java sources into vortex-module/src/ and Triton compiles them for you, at every start and on vortex reload.

What Vortex does

Every time Triton loads one of its classes, Vortex looks in the vortex-module/ folder first. If it finds a class there with the same full name, Triton runs that one instead of the copy in its jar. If it doesn't, Triton loads its own class as usual.

That gives you two things:

  • Overrides replace a class Triton already has, for example to fix or change how one part of Triton works.
  • Includes add classes Triton doesn't have at all, such as new skills or helper classes.

Vortex starts before the rest of Triton: Triton restarts its own Java process with Vortex as the system class loader, so every Triton class goes through it. Nothing else in Triton needs to know a class came from Vortex.

Vortex works on Triton itself, for everything running in Triton. To change a Triton class for one app only, use that app's mod/ folder instead (see Making apps).

vortex-module/

In Triton's main folder echo/, next to the Triton jar. Triton creates it on first start.

echo/vortex-module/
├── src/                       your .java sources: Triton compiles them
│   ├── system/                sources of overrides
│   │   └── echelon/ui/WindowFactory.java
│   └── tools/hello/Greeter.java   sources of includes
├── system/                    overrides: replace classes Triton has
│   ├── echelon/ui/WindowFactory.class
│   └── hotfix.jar             a jar of overrides
├── tools/hello/Greeter.class  includes: new classes, outside system/
├── new-feature.jar            a jar of includes
├── staging/                   classes waiting for the next start
├── snapshots/                 rollback copies Triton keeps
└── vortex_manifest.json       Triton's list of what is deployed
  • Classes sit at their package path, as in any classpath folder: echelon.ui.WindowFactory is system/echelon/ui/WindowFactory.class.
  • src/, system/, staging/, snapshots/ and plugin-data/ are reserved names. Don't use them as the first part of an include's package.
  • Don't edit vortex_manifest.json or snapshots/. Triton writes them.

Keep the source. A loose .class in system/ or among the includes must have its .java at the same path under src/. At every start and on vortex reload, Triton deletes loose classes whose source is gone. To ship compiled classes without their source, put them in a jar.

Overrides

An override replaces a class that is already in Triton's jar. Write its source under src/system/, at the class's package path, and Triton compiles it into system/:

echo/vortex-module/src/system/echelon/ui/WindowFactory.java
          → echo/vortex-module/system/echelon/ui/WindowFactory.class
  • The class must have exactly the same full name (package and class) as Triton's.
  • It replaces the whole class. Keep every public method and field that other classes use, with the same signatures, or the classes that call them break.
  • Inner classes (Name$Inner.class) come along with their outer class: Triton writes and removes them together.
  • Classes marked @Vortexable(Vortexable.Policy.LOCKED) can't be overridden (see @Vortexable).

Already compiled? Put the classes in a jar in system/ instead (see Jars).

Includes

An include is a class Triton doesn't have. Write its source under src/ (not src/system/), at its package path. Triton compiles it into vortex-module/ itself, outside system/:

echo/vortex-module/src/tools/hello/Greeter.java
          → echo/vortex-module/tools/hello/Greeter.class

An include may only add. If Triton's jar already has a class with that name, Vortex refuses the include, logs REJECTED INCLUDE and keeps Triton's class. To replace a class, put it under system/.

Sources Triton compiles

You don't have to compile anything yourself. Put .java files in src/ and Triton compiles them into the right place:

Source inCompiled into
src/system/echelon/ui/WindowFactory.javasystem/echelon/ui/WindowFactory.class: an override
src/tools/hello/Greeter.javatools/hello/Greeter.class: an include
Example · src/tools/hello/Greeter.java 
package tools.hello;

public class Greeter {
    public static String greet(String name) {
        return "Hello, " + name;
    }
}

Triton compiles a source when it is new (no .class yet), changed (the .java is newer than its .class), or was compiled by a newer JDK than the one Triton runs on now. It checks:

  • at every start, before Triton loads its own classes, and
  • whenever you run vortex reload in the Terminal.
  • The package line must match the folder. src/tools/hello/Greeter.java starts with package tools.hello;, and an override under src/system/echelon/ui/ starts with package echelon.ui;.
  • Sources compile against Triton's own classes and its lib/ jars, so they can use anything Triton has.
  • They compile for the Java version Triton runs on. Triton uses the JDK's compiler when there is one, and its built-in compiler otherwise, so a plain Java runtime is enough.
  • Delete a source and Triton deletes its compiled .class at the next check.

If a source doesn't compile, Triton shows the compiler's errors. Fix the source and run vortex reload again; the skills already running stay as they were.

Jars

A .jar is the way to add classes that are already compiled. It works like a folder of classes:

  • A jar in system/ holds overrides.
  • A jar directly in vortex-module/ holds includes, with the same rule: none of its classes may already be in Triton.
echo/vortex-module/system/hotfix.jar        overrides
echo/vortex-module/new-feature.jar          includes

Triton reads the list of jars when it starts, so a new jar is picked up at the next start. Triton never deletes a jar on its own. A loose .class file wins over the same class in a jar.

Staging

staging/ is for compiled classes you want Triton to take in at the next start. Use the same layout as vortex-module/ itself:

Put the class inAt the next start it becomes
staging/system/echelon/ui/WindowFactory.classan override in system/
staging/tools/hello/Greeter.classan include

When Triton starts, it moves each staged class into place, adds it to vortex_manifest.json and empties staging/. vortex scan tells you whether anything is waiting there.

A staged class becomes a loose class, so the keep-the-source rule applies: without its .java under src/, it is removed again at the start after that. For classes that should stay, add the source or use a jar.

When changes take effect

Java loads each class once. After that, the running Triton keeps using the copy it has. So:

ChangeTakes effect
Skills (in vortex-module/, compiled from src/)Right away with vortex reload: it recompiles and swaps the new skills into the running Triton.
An override of a class Triton has already loadedAt the next start.
A new jar, or classes in staging/At the next start.
A class Triton hasn't loaded yetThe first time Triton needs it.

When in doubt, restart Triton. vortex reload says so when classes are waiting for a restart.

Load order

For each class, Triton takes the first match:

  1. A class it has already loaded.
  2. Java's own classes (java.*, javax.*, sun.*, jdk.*), and Vortex's and the framework's (echelon.module.vortex.*, shared.*), always from the jar. Vortex can't replace them.
  3. A signed security patch from Strombos.
  4. A class marked @Vortexable(LOCKED): from the jar.
  5. An override in system/: loose .class, then system/ jars.
  6. An include in vortex-module/: loose .class, then jars.
  7. Triton's own class from its jar.

@Vortexable

Annotation echelon.module.vortex.Vortexable. Goes on a class in Triton.

@Vortexable says whether Vortex may override a class. Without it, a class can be overridden.

import echelon.module.vortex.Vortexable;

@Vortexable(Vortexable.Policy.LOCKED) // Vortex can't replace this class
public class SecurityCore { … }
ValueMeaning
no annotationThe class can be overridden. This is the default.
Vortexable.Policy.ABSORBABLEThe same, said on purpose.
Vortexable.Policy.LOCKEDSealed. Vortex refuses an override, logs REJECTED — class is sealed and loads Triton's own class.
Vortexable.Policy.INCLUDEMarks a new class that must not exist in Triton. Includes already work this way, so it only records intent.

Vortex reads the annotation on Triton's copy of the class. Removing it from your override changes nothing.

Triton seals its core classes this way, AbstractModule among them. It's not for app classes: leave it off your app's Main.

Terminal commands

Run these in the Terminal:

CommandDescription
vortex listShow what is deployed: system overrides, includes and jars
vortex scanShow sources that are new or changed, and classes waiting in staging; changes nothing
vortex reloadRecompile what changed, deploy it, and hot-swap the skills into the running Triton

Troubleshooting

Vortex writes what it does to the Triton log, each line starting with [Vortex].

You seeWhat it means · fix
REJECTED — class is sealedTriton's class is @Vortexable(LOCKED). It can't be overridden; Triton uses its own.
REJECTED INCLUDE — class already existsAn include has the name of a Triton class. Move it under system/ to override, or rename it.
Corrupt classThe .class file is damaged or not a class file. Compile it again.
LinkageErrorTriton had already loaded that class. Restart Triton.
The override doesn't seem to runCheck vortex list. Check that the source is under src/system/ at the exact package path, then restart Triton.
A .class you copied in disappearsIt had no .java under src/, so Triton removed it. Add the source, or put the class in a jar.
A source compiles but nothing is deployedThe package line doesn't match the source's folder. Make them match.
NoSuchMethodError or NoSuchFieldErrorYour override is missing something other classes use. Keep the original's public methods and fields.

To see every decision Vortex makes for Triton's classes, start Triton with -Dvortex.debug=true. It logs a lot, so turn it off again afterwards.

Nothing in this guide matches that filter.
